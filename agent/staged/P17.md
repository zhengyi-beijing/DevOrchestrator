# P17 — Backlog Reconciliation & Capability Baseline

## Objective
Reconcile the DevOrchestrator backlog against the implementation that actually exists after P1–P16.14. Establish an evidence-backed capability baseline before defining or starting any P18+ implementation work.

## Scope
For every backlog capability or objective, classify its current state as exactly one of:
- IMPLEMENTED
- PARTIAL
- NOT_IMPLEMENTED
- OBSOLETE
- MERGED

Do not classify from roadmap wording or historical claims alone. Trace conclusions to current source code, tests, runtime evidence, and relevant P1–P16 artifacts.

For PARTIAL items, record both the implemented portion and the concrete remaining gap. Rewrite stale backlog descriptions so they describe only remaining work and do not cause duplicate implementation.

At minimum reconcile:
- provider/model/account separation and AI routing
- quota telemetry, retry and provider/executor failover
- lifecycle authority, transition journal and successor handoff
- watchdog/activity evidence and recovery
- invariant/fault-injection control-plane framework
- post-Worker acceptance continuation / cross-executor recovery
- persistent project context
- control-plane API/web management surface
- multi-project lifecycle adoption
- project auto-onboarding
- task DAG / parallel execution
- multi-node execution
- mobile control surface
- operating/resource policy modes
- production-incident-to-regression/invariant self-improvement loop

## Required outputs
1. A cleaned canonical backlog with stale/duplicate items removed or rewritten.
2. A capability matrix with classification and evidence references.
3. Explicit residual gaps, technical debt, and known risks.
4. Candidate P18+ objectives derived only from verified remaining gaps.

## Acceptance criteria
- Every retained backlog item has an evidence-backed classification.
- IMPLEMENTED requires code plus test or runtime evidence where applicable.
- PARTIAL states implemented behavior and remaining behavior separately.
- MERGED identifies the canonical replacement objective.
- OBSOLETE explains why the item should no longer drive implementation.
- No new feature implementation is performed merely to make reconciliation look complete.
- P18+ candidates may be proposed, but P17 MUST NOT automatically invent or start P18.
- The repository and runtime evidence agree on the resulting capability baseline.

## Successor policy
P17 is the explicit successor of P16.14. It must be entered through the normal successor-handoff/control-plane path after P16.14 reaches accepted terminal completion. Do not manually launch P17.
