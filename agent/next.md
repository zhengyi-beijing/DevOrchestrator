## P15 goal

Provide an Android-native, failure-independent observation and bounded-control client without creating a second lifecycle authority.

Refer to `agent/staged/P15.md` for initial scope and acceptance criteria.

## Approved executable design

Deliver an Android-native observation and bounded-control client backed by a daemon-owned MobileGateway, without creating a second lifecycle authority. The external trust boundary is the authenticated MobileGateway: after authentication it may perform read-only in-process composition from existing authoritative projections and durable stores, while every mutation must traverse ControlAdapterClient and the authenticated loopback Control API. Mobile command provenance is durable and authorization-bearing: ControlCommandStore rejects any replay whose submitted source differs from the stored source, even when command_id and request body match. Mobile bearer tokens are never persisted in commands; the daemon injects one ControlSecurity-backed MobileDeviceAuthorizer into gateway ingress, loopback source admission, and ControlCommandCoordinator so execution revalidates the recorded device_id against the canonical capability store. Android notification thresholds remain presentation policy and never reclassify authoritative lifecycle state.

### Interfaces / contracts
- MobileDevicePrincipal(device_id: str, scope: 'mobile_device', created_at: str, expires_at: str | None, revoked: bool) contains no token or token hash and is the only device identity propagated beyond gateway authentication.
- MobileDeviceAuthorizer.validate_mobile_bearer(header_or_token: str | None) -> (ok: bool, reason: str, principal: MobileDevicePrincipal | None); MobileDeviceAuthorizer.lookup_mobile_device(device_id: str) -> (ok: bool, reason: str, principal: MobileDevicePrincipal | None); MobileDeviceAuthorizer.mobile_revocation_generation() -> int. Every operation reads runtime/control/adapter-capabilities.json and fails closed.
- ControlSecurity.create_mobile_pairing(*, expires_in_seconds) -> {pairing_id, code, expires_in_seconds}; redeem_mobile_pairing(pairing_id, code, device_label) -> {device_id, token, scope, expires_in_seconds}; revoke_mobile_device(device_id); revoke_all_mobile_devices(). The canonical file remains runtime/control/adapter-capabilities.json under InterProcessFileLock.
- ControlCommandStore.submit(value, *, source) retains the existing body request_hash but makes successful replay conditional on exact stored-source equality. Same command_id plus different source raises ControlCommandConflictError before any record is returned, covering control_api versus mobile and mobile device A versus device B.
- ControlAdapterClient.submit_control(adapter_request_id, project_id, action, expected_revision, target=None, *, source=None) sends X-DevO-Control-Source only for an explicit internal caller. MobileGateway supplies mobile_gateway:<authenticated device_id>; Android cannot supply this header through the mobile route.
- The loopback POST /api/v1/control/commands accepts X-DevO-Control-Source only with the master bearer and an injected MobileDeviceAuthorizer. A mobile source must match mobile_gateway:<safe device_id> and lookup_mobile_device must succeed at admission; missing or malformed headers use control_api, while a well-formed but invalid mobile claim is rejected.
- ControlCommandCoordinator(..., mobile_device_authorizer: MobileDeviceAuthorizer | None = None) performs execution-time lookup of the device_id parsed from the durable source. No bearer token is accepted by, stored in, or recoverable from the coordinator or command record.
- AIPlannerCoordinator.approve_owner_gate(project, snapshot, gate_id, command_id, binding_adapter=None, binding_id=None, *, approval_channel='conversation', approving_device_id=None) -> (bool, str). Mobile approval requires approval_channel='mobile_device' and a nonblank approving_device_id, which is persisted as audit metadata.
- mobile_owner_gate_eligibility(project, snapshot, runtime_root, device_id, mobile_device_authorizer, conversation_store, bridge_store) -> (available: bool, reason: str, gate_id: str | None) is shared by authenticated projection and execution guard; AIPlannerCoordinator performs the final state/repository recheck.
- MobileProjectionService(runtime_root, config_provider, mobile_device_authorizer).project_view(snapshot, project_config, principal) -> dict is a read-only in-process composition boundary. Direct runtime reads are permitted only inside this trusted daemon service; mutations are forbidden and all controls use ControlAdapterClient.
- Mobile HTTP surface: POST /api/v1/mobile/v1/pair; authenticated GET /projects, GET /projects/{project_id}, GET /events, POST /projects/{project_id}/controls, GET /commands/{command_id}, GET|PUT /alert-policy, POST /alerts/{alert_key}/ack, and POST /alerts/{alert_key}/snooze. Pairing credentials are invalid on authenticated routes.
- MOBILE_CONTROL_ACTIONS is the strict set {'continue','pause','resume','stop','retry','reconcile','approve_owner_gate'}. The projection and control route share it; rereview and bind, unbind, or rebind conversation actions are absent.
- evaluate_notification(progress_observation: Mapping | None, transport_observation: Mapping, policy: Mapping, now: datetime, ack_state: Mapping) -> NotificationDecision. Progress and transport classes and dedup keys are disjoint, and absent/stale/unavailable progress cannot produce progress-family alerts.
- Durable files are runtime/control/adapter-capabilities.json for authoritative device identity and revocation generation, runtime/mobile/alert-policy.json for notification policy, runtime/mobile/devices-telemetry.json for explicitly non-authoritative metadata, and runtime/mobile-gateway.json for health. Command records persist only source mobile_gateway:<device_id>, never bearer material.

### Risks / failure modes
- Command source becomes part of durable idempotency semantics without entering request_hash. Mitigation: compare the separately persisted source under the same command lock before returning any replay, conflict on every mismatch, test both replay directions and cross-device reuse, and preserve body hash compatibility for existing records.
- A forged mobile source could select a privileged approval branch. Mitigation: Android never supplies provenance; the gateway derives it from the authenticated principal, the loopback route requires master bearer plus tokenless live-device lookup, the command store source-locks replays, and the coordinator repeats lookup at execution time.
- Revocation can occur after gateway admission. Mitigation: inject the canonical authorizer into ControlCommandCoordinator, persist only device_id provenance, re-read canonical capability state immediately before mobile approval, and fail closed when the authorizer or store is unavailable.
- Separating bearer validation from device-id lookup could accidentally produce divergent rules. Mitigation: both operations are implemented by ControlSecurity over the same locked canonical store and share scope, expiry, revocation, and schema validation helpers; tests exercise admission-to-execution revocation.
- Direct runtime reads could be mistaken for a second authority. Mitigation: document MobileProjectionService as a trusted daemon-internal, read-only composition boundary, prohibit coordinator invocation and lifecycle writes there, and require every mutation to traverse ControlAdapterClient and existing DevO authority.
- The shared mobile eligibility predicate can become stale between projection and execution. Mitigation: treat projection availability as advisory, validate expected revision, call the predicate again in ControlCommandCoordinator, and retain AIPlannerCoordinator's locked pending-state and repository-truth rechecks.
- Binding a listener beyond loopback expands attack surface. Mitigation: default disabled, admit only verified local Tailscale addresses, refuse degradation or arbitrary allowlists, separate the handler from browser/loopback authentication, and fail closed on security-store errors.
- The pairing endpoint is the sole route without an established device bearer. Mitigation: high-entropy owner-minted credentials, hash-only storage, constant-time comparison, short TTL, one locked single-use redemption, attempt bounds, source rate limiting, and generic failures.
- Long-lived streams can outlive authorization and exhaust threads. Mitigation: revalidate before output and at bounded intervals, use revocation generation, cap streams per device and globally, implement heartbeat/idle timeout behavior, and provide equivalent long polling.
- Frequent stream revalidation contends with the shared capability file. Mitigation: keep non-authoritative telemetry outside the file, keep locks short, use the monotonic generation as a change signal without treating it as positive authorization, and preserve full canonical validation before sensitive output or execution.
- Notification policy could drift into lifecycle classification. Mitigation: keep progress and transport inputs, class names, and dedup keys disjoint; copy watchdog state verbatim; and use exhaustive invariants showing thresholds only suppress, delay, deduplicate, or escalate delivery.
- Android background execution and Doze can delay local notifications. Mitigation: use a foreground connection/notification channel, expose connectivity state honestly, and measure behavior during manual on-device acceptance rather than asserting hard delivery timing.
- The Android SDK is not guaranteed in the repository environment. Mitigation: make MobileContractClient the executable wire-contract acceptance harness and record Android build and physical-device checks as separate evidence.

### Out of scope
- The rereview control from mobile; it is absent from the staged P15 action set.
- Conversation-binding controls from mobile, including bind_conversation, unbind_conversation, and rebind_conversation.
- Any relocation or duplication of lifecycle authority; ControlCommandCoordinator, TransitionExecutor, AIPlannerCoordinator, AIReviewerCoordinator, and WatchdogCoordinator remain authoritative.
- Direct Android access to runtime files, durable stores, the loopback Control API, or coordinator objects.
- Lifecycle mutation by MobileGateway, MobileProjectionService, notification policy, or the Android client.
- Persisting mobile bearer tokens in command records, plan records, audit logs, telemetry, or source strings.
- Any additional unauthenticated-device ingress beyond the single pairing-credential route.
- Any bind target other than a verified local Tailscale interface address, including arbitrary owner allowlists, private LAN, public, wildcard, or reverse-proxy exposure.
- Weakening the existing browser owner-gate path, loopback control requirement, browser CSRF behavior, or ChatGPT CORS allowlist.

- Changing watchdog stall classification, thresholds, recovery-epoch resolution, diagnostics classification, or authoritative freshness rules.

- TLS termination, public-internet deployment, or transport security beyond the existing Tailscale boundary.
