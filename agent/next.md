# P16.7 Self-Healing Project Activation & Readiness

Status: **READY_TO_RUN**

## Goal

Use the 2026-09-23 xray-hw-platform activation failure as the concrete regression case to make DevOrchestrator diagnose and recover project-activation/readiness failures without requiring repeated owner messages such as "继续", "目前状态", or "修复这个问题".

The observed failure chain was:
1. repository-local `.devorch/status.json` still showed an old P4.1/REVIEW_FAILED state while the running daemon did not have `xray-hw-platform` registered at all;
2. `project-status xray-hw-platform` returned `not_found`;
3. after project registration and P1 task/contract anchoring, `continue` still failed with `project is not READY_TO_RUN`;
4. the task projection used human-readable `READY / OWNER_GOAL_DEFINED / NOT_STARTED`, while `resolve_monitor_state()` accepted only `READY_TO_RUN`, `DESIGN READY`, or `EXECUTABLE`, so the project was projected as `IDLE`;
5. changing the token to `READY_TO_RUN` caused the daemon to auto-launch the P1 AIBroker Worker successfully;
6. transient RDC inspection timeouts also caused orchestration work to stop and require another owner message even though no true owner decision was required.

## Required outcomes

### 1. Authoritative state and orphan detection
- Explicitly distinguish daemon-authoritative runtime state from repository-local historical/projection state.
- If local DevO state exists but the project is absent from the active registry, surface a structured `ORPHANED_PROJECT_STATE`/equivalent diagnosis rather than presenting stale lifecycle state as current truth.
- Where project identity/path/config are unique and validation succeeds, support bounded register/reconcile recovery; otherwise surface a precise blocker rather than guessing.

### 2. Structured readiness contract
- Remove critical lifecycle authority from free-form Markdown regex matching.
- Introduce a machine-readable readiness/execution state contract (for example `execution_state=ready_to_run`) with schema/version validation.
- Markdown such as `agent/next.md` is a human projection of structured state, not the authoritative protocol.
- Preserve a bounded legacy parser/migration path so existing projects do not break abruptly.
- Invalid/ambiguous readiness values fail closed with an actionable diagnostic.

### 3. Structured blocker diagnostics
- A rejected transition such as `continue` must return the failed predicate(s), expected value, observed value, evidence source, and bounded remediation.
- Add one canonical blocker/explain surface usable by CLI, API, Web UI, mobile and watchdog (for example `explain-block` or `GET /projects/{id}/blockers`).
- For the reproduced incident, diagnostics must identify the readiness-token/state mismatch directly instead of only returning `project is not READY_TO_RUN`.

### 4. Continuous self-recovery
- Classify failures into at least transient infrastructure, recoverable orchestration, owner gate, and terminal outcomes.
- Transient failures such as RDC/SSH/broker timeouts and recoverable conditions such as stale registration/readiness projection must not silently return control to the owner.
- Apply bounded retry/backoff and safe alternate inspection/reconciliation where available.
- Persist the original Start/Continue execution intent across remediation. A successful remediation is not terminal: DevO must retry the original forward transition automatically.
- Implement a bounded auto-recovery loop with independent budgets for total recovery actions, repeated identical failures, and elapsed launch time. Initial defaults for acceptance are 20 recovery actions, 3 repeats of the same failure fingerprint, and 30 minutes elapsed; keep them configurable and tune from replay evidence.
- Track a recovery fingerprint containing at least project/task, lifecycle state, blocker code, Git anchor, Worker state, and broker state. Detect no-progress and short cycles (for example A->A and A->B->A->B) and fail closed rather than spinning.
- While an execution intent targets EXECUTING, and there is no OWNER_GATE, explicit stop, terminal failure, or exhausted recovery budget, DevO must eventually attempt another forward transition without another owner message.
- Stop only for a genuine owner-only decision, explicit stop, terminal success, exhausted bounded recovery budget/livelock, or an invariant violation that cannot be recovered safely.

### 5. Idempotent/race-safe control
- If an execution is already active, a duplicate `continue` must resolve deterministically as an idempotent no-op such as `NOOP_ALREADY_EXECUTING`, not create an ambiguous pending command.
- Bind transition commands to project/task/head/recovery epoch/control identity and fail closed on stale identity.
- Prove that monitor auto-start racing with an explicit continue cannot launch duplicate Workers.

### 6. Git-truth diagnostics
- Keep clean immutable Git execution anchors as the launch authority.
- Distinguish expected owner-approved task artifacts from unexpected dirty changes in diagnostics.
- Never silently commit or discard unexpected changes solely to obtain a clean anchor.

## Acceptance regression

Build an automated regression that recreates the exact incident:
- stale repository-local P4.1/REVIEW_FAILED projection;
- project absent from active registry;
- valid P1 task contract exists;
- readiness initially represented as legacy `READY / OWNER_GOAL_DEFINED / NOT_STARTED`;
- transient inspection failure is injected;
- project is safely registered/reconciled;
- readiness is normalized/migrated to structured `ready_to_run`;
- blocker diagnostics identify every failed predicate during recovery;
- exactly one Worker is launched;
- duplicate `continue` during/after auto-launch returns an idempotent no-op;
- no owner interaction is requested unless a true owner-gate condition is injected.

Acceptance evidence must include lifecycle/command audit records proving the transition sequence and demonstrating that stale local state was never treated as daemon-authoritative truth.

## Priority

Within P16.7, prioritize:
1. structured readiness instead of Markdown regex authority;
2. structured blocker/explain diagnostics;
3. transient/recoverable automatic recovery;
4. orphan registration reconciliation;
5. richer Git dirty classification.

## Non-goals

- Do not weaken owner gates for architecture, public interfaces, resource ownership, threading, protocol/replay semantics, destructive Git operations, or physical safety.
- Do not auto-start real hardware, X-ray sources, conveyor/VFD, or other safety-sensitive resources.
- Do not make stale local files authoritative over the daemon/control ledger.
- Do not solve the problem by adding more permissive regex aliases alone; the objective is to remove free-form text as lifecycle authority.

## Approved executable design

Make DevOrchestrator diagnose and self-heal project-activation/readiness failures without repeated owner messages, replaying the 2026-09-23 xray-hw-platform incident as the acceptance regression. Introduce agent/execution-state.json (schema_version 1) as the machine-readable readiness authority, bound to the current task: any structured file whose task_id differs from the current agent/next.md task fails closed before lifecycle projection and before any launch, and staged-successor activation writes pending_design for the new task atomically in the same commit as agent/next.md, so a prior task's ready_to_run can never launch an unplanned successor. A bounded closed legacy component grammar resolves the incident token READY / OWNER_GOAL_DEFINED / NOT_STARTED deterministically into a migration candidate that an explicit audited authority predicate set may write as structured ready_to_run. Add one canonical structured blocker/explain surface reachable for registered projects by id and for unregistered repositories by path. Define the bootstrap authority explicitly: an owner-supplied activation request (CLI project-activate --repo, Control API) is the single origin of candidate project identity, repo path and worker configuration; it creates a durable request plus an execution intent carrying those candidates, which the supervisor validates, registers atomically into config/projects.json and then drives forward. Add a durable execution-intent ledger and a bounded per-tick self-recovery supervisor classifying failures as transient_infrastructure, recoverable_orchestration, owner_gate, recovery_exhausted or terminal under independent budgets (20 actions, 3 identical fingerprints, 30 minutes, configurable). Exhaustion and livelock are a distinct terminal fail-closed classification that never fabricates an owner gate, and the watchdog is changed in one bounded, intent-gated place so its max_attempts exhaustion and non-genuine owner-gate emissions become a supervisor handoff instead of a persisted OWNER_GATE. Keep genuine owner gates, Git-anchor authority and daemon-authoritative state unchanged, and add idempotent NOOP_ALREADY_EXECUTING semantics so duplicate continue and watchdog auto-start cannot double-launch a Worker.

### Implementation steps

Return a frozen ReadinessResolution(state, source, task_id, valid, stale, code, reason, migration_candidate, migration_required). Unknown keys, wrong schema_version, unparsable JSON or an out-of-vocabulary value fail closed with state='invalid' and an actionable code. The monitor side stays strictly read-only.
- Define the bounded legacy grammar in readiness.py as the single authoritative rule that makes the incident token implementable. With the structured file absent, split the one agent/next.md 'Status:' line on '/' and map each trimmed case-folded component through a closed table: READY|READY_TO_RUN|DESIGN READY|EXECUTABLE -> design_ready; PENDING DESIGN -> pending_design; BLOCKED -> blocked; COMPLETE|ACCEPTED -> completed; OWNER_GOAL_DEFINED|OWNER_APPROVED -> owner_goal_defined (no state of its own); NOT_STARTED -> not_started; IN_PROGRESS|RUNNING -> executing; DONE -> completed. design_ready plus not_started yields migration_candidate='ready_to_run'. Any unknown component, any conflicting pair, or more than one Status line yields no candidate and code READINESS_TOKEN_UNRESOLVABLE with the raw token as observed evidence.
- Bind readiness to the current task and fail closed on drift. resolve_readiness takes the current task id (snapshot telemetry / agent/next.md title) and, when a structured file's task_id does not equal it, returns state='invalid', stale=True and code READINESS_TASK_ID_MISMATCH carrying both ids. ### Risks / failure modes
- Readiness drift is the sharpest failure mode: a structured file left by a superseded task could launch unplanned work. The task-id binding check, the successor-activation pending_design write and explicit launch-guard refusal must land together, with a test that activates a successor over an existing ready_to_run file.
- Adding agent/execution-state.json to the successor-activation and plan-freeze commits touches the clean-anchor invariant. Use one add/commit pair with explicit pathspecs, extend the existing rollback to restore both files, and assert the resulting HEAD is clean in planner and staged-handoff tests.
- Changing the watchdog exhaustion branch is a behaviour change in a hardened component. Gate it strictly on an active, epoch-matching execution intent so every path without an intent is untouched, and prove both branches by test.
- Suppressing watchdog owner gates could hide a genuine owner-only decision. Translate only reasons classified transient_infrastructure, recoverable_orchestration or recovery_exhausted; owner_gate and terminal reasons keep emitting exactly as today.
- resolve_monitor_state and _next_task_ready are consumed across monitor, executor, control commands, watchdog and mobile projection; moving readiness authority can silently shift lifecycle. Keep the return vocabulary, keep the legacy live projection byte-identical, route every caller through one resolver, and run the full suite before closing the step.
- The legacy component grammar is the one place a human token becomes a machine decision. Keep it closed, reject unknown and conflicting components, and let it produce only a candidate the authority predicates must still approve.
- Programmatic editing of config/projects.json is new ownership of an owner-authored file. Restrict it to a validated, unique, profile-backed candidate from an explicit activation request, append only, write atomically, and fail closed rather than merging ambiguous entries.
- The bootstrap still requires one owner-supplied repo path; if the activation surface is missed, an orphaned project is diagnosable but not recoverable. Cover explain-block path mode and the activate-to-launch chain so the single required owner action is proven sufficient.
- The self-recovery loop can spin or fight the watchdog. Shared deterministic command ids, recovery-epoch binding, handoff consumption, fingerprint cycle detection and the three budgets must all be in place before the supervisor is wired into the tick.
- Budget defaults (20 actions, 3 repeats, 30 minutes) are initial acceptance values that may be wrong under real RDC latency; configurability and evidence tuning are part of the contract, not a follow-up.
- An over-broad transient classification could mask a genuine terminal failure and retry silently. Default unknown failures to terminal, and classify as transient only markers already recognized in core/diagnostics.py.
- Persisting intent across restarts risks resurrecting a forward transition after an owner stop or pause. Revalidate control identity, pause state and owner gates on every attempt and clear the intent on any explicit stop.
- Windows/PowerShell specifics: concurrent atomic JSON writes and path canonicalization have bitten this repo before; reuse storage.json_store helpers and existing watchdog path canonicalization, and avoid && or || in any PowerShell 5.1 command.
- Scope breadth could produce an unreviewable change. Land the work in the stated priority order (structured readiness and its task binding, blockers, recovery plus watchdog coordination, orphan reconcile, Git classification) with tests at each step.

### Out of scope
- Weakening or bypassing genuine owner gates for architecture, public interfaces, resource ownership, threading, protocol/replay semantics, destructive Git operations, or physical safety.
- Auto-starting real hardware, X-ray sources, conveyor/VFD or any safety-sensitive resource; the xray-hw-platform incident is replayed only as an activation fixture.
- Automatic filesystem discovery or scanning for unregistered repositories; candidate identity, path and worker configuration come only from an explicit activation request plus a configured activation profile.
- Making .devorch/status.json or any repository-local historical file authoritative over the daemon registry and control ledger.
