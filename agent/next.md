- Run binding authority: an append-only reliability run registry owned by the new reliability module (records schema_version, run_id, project_id, opened_at, closed_at, wall and monotonic anchors, daemon boot_id at open, opener source). Membership rule: a source event belongs to run R iff project_id matches R.project_id, its durable recorded time (occurred_at/recorded_at/observed_at/created_at per ledger) is within [opened_at, closed_at or now), and any run_id/boot_id the ledger carries matches R.
- Double-count rule: every metric has exactly one primary ledger; other ledgers may only corroborate coverage, never add. Cross-ledger reconciliation happens solely through shared identity keys (command_id, attempt_id, gate_id, transition_id, idempotency_key, job_id, failure_signature+occurrence_key, boot_id). Each metric returns value plus source, identity key, dedup rule and coverage in {full, partial, unknown} with reason; unknown is never rendered as 0.
- Metric sources 1/4: manual_continue_count from runtime/control/audit.jsonl plus control command records, identity command_id, counting distinct accepted action==continue commands whose source is an owner source (sources beginning automatic_, such as automatic_review_handoff, are excluded, which is what keeps the CPF-09 automatic replay out of the manual count); unknown when a matching command lacks a source field. owner_gate_count from accounting owner_gate_opened events, identity gate_id, reconciled with the control surface gate by the same gate_id (the CPF-08 CONTROL_PLANE_DECLARATION_REQUIRED gate counts once); unknown when gate_id is absent.
- Metric sources 2/4: duplicate_execution_count from runtime/transition-executor.json executions, identity the execution key (project_id, source_request_id, task_id), counting more than one active execution identity for one logical request (a CPF-01 stale predecessor Worker under a fenced target is not a duplicate). duplicate_handoff_count from the same file's transitions/handoff_record consumption, identity idempotency_key, counting more than one consumption of one handoff (a CPF-02 rebuilt single handoff counts zero duplicates). duplicate_successor_activation_count from published transitions, identity transition_id, per (source_task_id, target_task_id, generation). duplicate_job_count from runtime/jobs/index.json, identity (idempotency_key, job_id).

### Risks / failure modes
- Counter-count discrepancy: agent/next.md says 16 counters while owner section 3 and agent/staged/P20.md name 15. Accepted resolution (reviewer non-blocking): implement the 15 named metrics plus an explicit recovery_latency_sample_count, documenting the arithmetic in the contract doc rather than inventing an unnamed counter.
- Several metrics cannot be fully covered before P20.2/P20.3 exist (automatic recovery, strategy evidence); the mitigation is the mandatory per-metric coverage field (full/partial/unknown with reason) so P20.1 never reports a dishonest zero and later stages raise coverage without changing metric names.
- Time-window run binding can misattribute events if a ledger lacks project_id or a usable durable timestamp; mitigated by requiring both project and time match, honouring any ledger-carried run_id/boot_id, and reporting unknown coverage instead of guessing.
- The CPF-01 through CPF-10 observation assertions are new reliability observations layered on existing scenario behaviour; if a scenario fixture does not expose the identity key a metric needs, the correct outcome is coverage unknown plus a documented gap, never a changed scenario fixture or a relaxed registered CPF test.
- The daemon boot record is a runtime-sensitive change to daemon startup and touches the CPF-03 restart path; mitigated by the section-16 preflight, ledger backup, append-only single-line write beside the existing daemon.json write, and daemon regression tests. Do not restart the daemon while a Worker runs.
- A persistent fence blocks all incident capture after one bad index, and P20.1 intentionally has no clearing API; mitigated by a documented manual owner procedure, typed actionable errors, and tests proving no relaunch and no self-clearing occur while fenced. If the owner later wants a programmatic clear, it belongs in a reviewed follow-up through existing owner control APIs.
- Global capacity caps risk losing failures or evicting replay dedup keys and permitting re-actuation; backpressure must be explicit and dedup keys exempt from eviction.
- Extending the fingerprint allowlist could split or merge existing P16.10 families; mitigated by keeping current semantic payload results byte-identical and introducing new fields only through the new contract path.
- Aggressive sanitization can strip diagnostic value needed by P20.2 harvesting; prefer bounded typed evidence references and test both redaction and retained diagnostics.
- Concurrency, lock and restart tests can be flaky on Windows; prefer deterministic multi-process/lock-ordering fixtures over sleep-based timing.
- Scope creep into P20.2 detectors or P20.3 recovery policy would break the review-gated sequence; harvesting detector coverage stays unchanged except where contract validation requires it.
- Known pre-existing hypotheses (capture reads families before the transaction, quarantine unlinks index.json, legacy evidence copied unsanitized, unbounded family growth) must be proven by RED tests before being changed, and no existing evidence may be deleted to repair them.
