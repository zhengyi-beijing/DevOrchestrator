# P9 D2 Durable Project Context Foundation

Status: **COMPLETED** (Ready for independent review)

Goal: make project-specific durable context a first-class DevOrchestrator input so any control conversation can continue a project without relying on chat memory.

Required context domains: project goals, architecture/module responsibilities, protected scope and safety constraints, build/test/validation commands, deployment/runtime assumptions, and durable key decisions.

Design constraints:
- explicit project/repository context remains authoritative; generated context is supplemental;
- inject bounded context into Planner, Worker/Remediator, and Reviewer requests without exposing credentials or unrelated user data;
- preserve project isolation and fail closed on malformed context;
- Graphify may be used as an optional structure/dependency source, but DevO must not require Graphify at runtime;
- provide a stable schema/versioning/update path suitable for later automatic onboarding;
- expose enough context/status metadata for future Control API/dashboard use.

Scope: modify only C:\work\github\DevOrchestrator-dev. No stable-controller modification/restart/promotion, no push, and no physical hardware actions.

Acceptance: focused regressions + full unittest suite + browser userscript syntax check + git diff check; update agent docs and commit locally clean; independent reviewer must accept before any later owner-gated promotion.

## Approved executable design

Add a durable, project-scoped context foundation to DevOrchestrator: a versioned context document schema (goals, architecture, protected scope/safety constraints, validation commands, runtime assumptions, key decisions), an opt-in per-project declaration in projects.json, a fail-closed resolver that treats the explicit repo/config document as authoritative and an optional generated file (e.g. a Graphify export) as supplemental only, a bounded deterministic prompt block injected into Planner, plan Reviewer, Worker/Remediator and Reviewer requests, and context status metadata surfaced through project snapshots, the .devorch status mirror, validate-config and a new read-only CLI command. No Graphify import or process is required at runtime; no stable-controller change, no push.

### Implementation steps
- Add new module src/dev_orchestrator/core/project_context.py defining PROJECT_CONTEXT_SCHEMA_VERSION = 1, CONTEXT_DOMAINS = ("goals","architecture","protected_scope","safety_constraints","validation_commands","runtime_assumptions","key_decisions"), DEFAULT_DOCUMENT_RELATIVE_PATH = "agent/project-context.json", and frozen dataclasses ProjectContextDocument(schema_version, project_id, updated_at, domains: dict[str, tuple[str, ...]], provenance: dict[str, str], digest) and ProjectContextResolution(state, reason, document, sources, status). Keep the module dependency-free apart from pathlib/json/hashlib and dev_orchestrator.storage.json_store, matching existing Core module style (module docstring, from __future__ import annotations, no product-name branching).
- Implement strict fail-closed document validation in project_context.py: validate_context_document(payload, *, expected_project_id) requires exactly {schema_version} + the seven domain keys plus optional {project_id, updated_at}; rejects unknown top-level keys, schema_version != 1 (with an explicit 'unsupported project context schema_version' reason reserved for future migration), non-list domains, blank/non-string entries, more than 40 entries per domain, entries longer than 600 chars, and a project_id that does not match the configured project_id (project isolation). Reject any entry matching a bounded secret marker set (case-insensitive 'password', 'api_key', 'api key', 'secret', 'token', 'bearer ', 'client_secret', 'private_key', '-----BEGIN') so credentials can never reach a prompt; return (document|None, reason).
- Implement path and source resolution in project_context.py: resolve_document_path(repo_path, declared_relative) rejects absolute paths, drive-qualified paths, and any path escaping the repository after Path.resolve() (project isolation, no cross-project reads); load_declared_document(project) reads the resolved repo file as UTF-8 (utf-8-sig tolerant) and maps OSError/JSON errors to explicit reasons; load_supplement(project) reads the optional supplement file with the same validator but all domains optional, and treats a missing supplement as absent rather than an error.
- Implement precedence and merge in project_context.py: resolve_project_context(project) returns a ProjectContextResolution whose state is one of 'absent' (not declared), 'ready', or 'invalid'; the declared document is authoritative and a supplemental domain value is used only when the corresponding declared domain is empty, recorded per-domain in provenance as 'declared' or 'generated'; a malformed or missing declared document while declaration is enabled yields state='invalid' with an explicit reason; compute digest = first 16 hex chars of sha256 over canonical json.dumps(sort_keys=True) of the merged domains for change detection; never raise out of this function (unexpected errors become state='invalid').
- Implement bounded rendering in project_context.py: render_context_block(document, *, max_chars) emits a deterministic block delimited by [PROJECT_CONTEXT_BEGIN]/[PROJECT_CONTEXT_END] with a header line carrying schema version, digest and per-domain provenance, fixed domain order, '- ' bullet entries, generated-provenance domains labelled '(supplemental, unverified)', and truncation at the entry boundary with an explicit '[PROJECT_CONTEXT_TRUNCATED]' marker so a partially rendered block is always self-describing; add context_prompt_block(project, role) -> tuple[str, ProjectContextResolution] returning ('' , resolution) when state != 'ready' or when role is not in the configured inject_roles.
- Extend src/dev_orchestrator/config.py to normalize and structurally validate an optional per-project 'project_context' declaration object with keys {enabled (bool, default false), document_path (non-blank repo-relative string, default agent/project-context.json), supplement_path (optional non-blank string), require_valid (bool, default true), max_chars (int, clamped 500..20000, default 6000), inject_roles (non-empty subset of planner|worker|reviewer, default all three)}; reject unknown keys, wrong types and invalid role names with explicit ValueError text consistent with existing config errors; mirror the normalized block onto the returned project copy and leave orchestration_ready semantics unchanged.
- Inject context into planning in src/dev_orchestrator/core/ai_planner.py: in AIPlannerCoordinator.start, resolve the context once, refuse the lifecycle with (None, reason) when the declaration is enabled, require_valid is true and state == 'invalid' (fail closed), and store the rendered block plus context status metadata (state, digest, sources) on the plan record; append the block to both _planner_prompt and _review_prompt output between the existing instruction text and the agent/next.md section, keeping the exact existing JSON-contract wording and parser unchanged.

### Interfaces / contracts
- src/dev_orchestrator/core/project_context.py public surface: PROJECT_CONTEXT_SCHEMA_VERSION, CONTEXT_DOMAINS, DEFAULT_DOCUMENT_RELATIVE_PATH, ProjectContextDocument, ProjectContextResolution, validate_context_document(payload, *, expected_project_id) -> tuple[ProjectContextDocument | None, str], resolve_project_context(project) -> ProjectContextResolution, render_context_block(document, *, max_chars) -> str, context_prompt_block(project, role) -> tuple[str, ProjectContextResolution], context_status(resolution) -> dict[str, Any].
- Durable context document (default <repo>/agent/project-context.json, schema_version 1): required keys schema_version, goals, architecture, protected_scope, safety_constraints, validation_commands, runtime_assumptions, key_decisions; optional project_id and updated_at; every domain is a list of at most 40 non-blank strings of at most 600 characters; unknown keys are rejected.
- projects.json project entry gains optional project_context = {enabled: bool=false, document_path: str="agent/project-context.json", supplement_path: str|null, require_valid: bool=true, max_chars: int=6000 clamped 500..20000, inject_roles: ["planner","worker","reviewer"]}; legacy configurations without the block behave exactly as today.
- Prompt injection contract: the rendered block is appended to the existing planner, plan-reviewer, worker, remediation and reviewer prompts between [PROJECT_CONTEXT_BEGIN] and [PROJECT_CONTEXT_END] with a schema/digest/provenance header and an optional [PROJECT_CONTEXT_TRUNCATED] marker; all existing role JSON output contracts, decision tokens and parsers stay unchanged.
- Status metadata contract: project_context = {schema_version, state: absent|ready|invalid, reason, digest, updated_at, document_path, supplement_used, domains: {<domain>: <entry count>}} attached to runtime/projects/<id>.json, runtime/summary.json, <repo>/.devorch/status.json (schema_version unchanged at 1, additive key) and returned by the CLI; it never carries credentials or raw prompt text.
- CLI surface: new read-only `dev-orchestrator project-context --config <path> --project-id <id>` returning JSON and exit 1 on invalid context; `validate-config` project rows gain project_context_state and project_context_error.
- Optional supplemental producer contract: any tool (including Graphify) may write the supplement JSON at the configured supplement_path using the same domain vocabulary; DevOrchestrator only reads that file, never imports or launches the producer, and a missing/unreadable supplement degrades to declared-only context.

### Risks / failure modes
- Fail-closed refusal on invalid context could stall a live lifecycle; mitigated by declaration being opt-in (enabled defaults to false), by the require_valid escape hatch, and by emitting explicit blocked/failed reasons instead of silent stalls.
- Prompt growth could crowd out task instructions or increase broker cost; mitigated by the clamped max_chars budget, bounded per-domain entry counts/lengths, and deterministic truncation with an explicit marker.
- Leaking credentials or unrelated project data into prompts; mitigated by strict string-only validation, the secret-marker rejection set, repo-confined document paths, project_id match enforcement, and status metadata that excludes raw content.
- Touching transition_executor.py prompt composition risks disturbing the reviewed-remediation anchoring and fresh-guard semantics that earlier acceptances depend on; mitigated by appending only, leaving the default prompt constants and guard order untouched, and re-running the existing executor suites.
- A monitor-tick resolution error could break snapshot writing for all projects; mitigated by wrapping resolution per project and degrading to state='invalid' metadata instead of raising.
- Schema strictness (unknown keys rejected) can break forward compatibility if a future producer adds fields; mitigated by documenting the schema_version 1 -> 2 additive migration path and rejecting unknown versions with an explicit, recognizable reason.
- Digest instability across runs would cause noisy status churn; mitigated by canonical sorted-key JSON hashing over merged domains only and a determinism test.

### Out of scope
- Any modification, restart or promotion of the stable controller at C:\work\github\DevOrchestrator; no git push and no physical hardware action.
- Automatic onboarding or automatic generation of context documents from a repository scan; this task delivers the schema, resolver, injection and status surfaces only.
- Importing, invoking, bundling or depending on Graphify at runtime, and defining a Graphify-specific export format beyond reading the generic supplement file.
- New dashboard HTML/JS views or new web/bridge HTTP routes; context metadata rides existing /api/summary and /api/projects/<id> payloads.
- Cross-project or global shared context, context inheritance between projects, and any write-back of generated context into an observed repository.
- Changing role JSON output contracts, decision vocabularies, lifecycle state machines, plan-freeze rendering in agent/next.md, or existing progress-channel event semantics.
- Conversation/chat-memory persistence, transcript storage, or any credential/secret store integration.
- Multi-version schema migration tooling; schema_version 2 is documented as a future path only.
