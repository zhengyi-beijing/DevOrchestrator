# P20.4 — Fault-Injection Multi-Task Unattended Soak

Status: **READY_TO_RUN**

Predecessor: P20.3
Successor: P20.5

## Objective and frozen direction

Build the isolated reproducible tracked software template/harness defined in
`agent/staged/P20.md` and `docs/P20_OWNER_REQUIREMENTS.md` sections 6, 8–11, 18.
Disposable generated Git repo and runtime must be outside the production
checkout. Local explicit soak permit only, defaults OFF, no remote enablement,
hardware, RDC, production fault injection or direct lifecycle ledger writes.

Run five real bounded feature/edge-case/refactor/parser/API tasks through real
Planner/Worker/tests/commits/independent Reviewer, AIBroker/resource routing,
durable jobs and lifecycle. Test/inject all 15 specified faults and record
actual incidents, stable family identities, recovery strategy/outcomes and
correct owner gates. Separate deterministic proof from live fault coverage.

## Hard duration gate and durable ownership

One real continuous unattended run >=21600 seconds; UTC/boot-aware monotonic
start/end/duration, restart/task/incident/recovery timelines. No fabricated
clock or summed old runs. A detached DevO-owned durable supervisor must survive
this session and daemon restarts. Keep P20.4 RUNNING until evidence satisfies
the real-duration gate. Launching a harness does not complete the phase.
Never count implementation preparation or sleep-only time as a live soak.
Do not permit automatic technical review/next_task while the soak is running.
If a foreground Worker cannot retain ownership, use the existing observable
durable external-wait contract rather than marking that Worker completed.

## Acceptance and checkpoint

TDD proves permit/path/project isolation and each fault. Live qualification
requires five accepted real tasks, six continuous hours, zero manual continue
or lifecycle repair, zero duplicates/escapes/stalls/loops/regression, 100%
fault disposition and incident coverage. Correct owner gates remain stable,
actionable and inhibit effects. Record run ID/start/elapsed/tasks/incidents/
recovery/current execution/next fault and exact resume command in HANDOFF.
Resume the same run after session loss, never reset its start. Only after
independent Technical Review ACCEPT may P20.5 activate. No push.

### Risks / failure modes
- The running production daemon has already imported the current code, so installing a binding from a new CLI process while the old daemon still completes on Broker success could publish a premature completion. Mitigation: commit the binding-aware code, perform a normal controlled daemon stop and start, verify fresh runtime identity and same-source ownership, then install the binding and start the run.
- A session-owned foreground Worker cannot hold a six-hour run. Mitigation: ownership stays in the TransitionExecutor execution record bound to a JobService-owned detached supervisor, and the harness launch itself never marks the phase complete.
- A daemon or supervisor crash could leave ambiguous job identity and tempt a duplicate supervisor (CPF-01, CPF-07). Mitigation: reconcile through JobService status and start_token, and gate with a durable OWNER_GATE on unknown liveness instead of re-dispatching.
- Suppressing Worker completion risks masking a genuine stall. Mitigation: bound the external wait with a deadline and heartbeat-age threshold that still breaches, producing an incident and an actionable gate rather than silence.
- Fault injection could escape into the canonical checkout, the production runtime, the production daemon or the production Broker. Mitigation: permit-validated canonical path containment and process identity checks on every target, refusal tests, and a disposable or isolated transport boundary for broker unavailability.
- Windows path realities (junctions, short paths, case-insensitive overlap, long-path limits) can defeat naive containment checks. Mitigation: canonicalize with resolved real paths, compare case-insensitively, and reject any unresolvable or ambiguous path.
- time.monotonic() is boot-relative on Windows, so a reboot or clock change could corrupt duration math. Mitigation: store boot identity and boot time with every checkpoint, compute per-segment deltas, and fail acceptance explicitly on discontinuity.
- Re-exercising CPF-04 style contradictory successor claims inside the soak could disturb the real P20.4 to P20.5 lineage. Mitigation: run successor-ambiguity scenarios only inside the disposable soak project or as isolated child probes, and keep successor activation suppressed for the production project while the binding is active.
- Real AI tasks and injected faults may legitimately produce a correct OWNER_GATE that halts the five-task chain. Mitigation: model unsafe faults as isolated child probes or terminal scenarios and order the schedule so chain-blocking cases run last.
- Real provider quota, cost or availability limits over six hours could stall the five-task chain. Mitigation: bounded tasks, existing resource routing and failover, honest incidents for exhaustion, and a correct gate rather than fabricated coverage.
- Writing the escaped_to_authority producer could misclassify a fenced launch as an escape and fail the hard-zero gate spuriously. Mitigation: require explicit actuation evidence, add tests for both the fenced and escaped cases, and keep UNKNOWN when evidence is missing.
- Two daemons, two runtime roots and two broker endpoints on one host risk port or lock collisions. Mitigation: recheck and bind ports atomically at launch, keep every soak lock and ledger under the disposable runtime, and never touch production ports or locks.
- Six hours of soak evidence could exhaust bounded incident, candidate and journal storage. Mitigation: reuse the existing bounded storage with backpressure and owner gating, keep soak evidence in the disposable runtime, and never evict replay dedup keys.
- The soak may still be running when this session ends. Mitigation: HANDOFF records the run id, start, elapsed and exact resume command, and P20.4 stays RUNNING with no fabricated completion.
