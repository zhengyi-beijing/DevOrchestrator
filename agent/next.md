# P11x Deferred Staged Handoff (Planner-Owned Materialization)

Status: **COMPLETE**

Owner authorization: **START P11x / 2026-09-13**

Goal: after an accepted technical review completes one task, automatically start the explicitly approved successor task without a new `project-continue`, while keeping repository mutation exclusively inside the existing Planner apply boundary.

Owner-decided architecture — freeze this direction:
- TransitionExecutor/control plane MUST NOT modify `agent/next.md`, staged specs, or create Git commits for task handoff.
- The explicit roadmap only selects a successor and its staged task specification.
- A handoff record carries successor task id, spec path/digest, reviewed branch/HEAD and source_request_id.
- ControlCommandCoordinator resumes that handoff by starting the Planner with an explicit task/spec override even though the repository still advertises the completed predecessor.
- Before plan approval the repository HEAD and `agent/next.md` must remain unchanged.
- On approval, AIPlannerCoordinator alone materializes the successor: validate the same clean HEAD, validate predecessor `agent/next.md` is unchanged, validate staged spec digest is unchanged, render the successor spec to READY_TO_RUN with the approved design, and use existing `_commit_plan()` for exactly one commit.
- Reuse existing handoff idempotency (`source_request_id`, deterministic continuation id, `handoff_consumed`, plan-id reuse). Do not add a second Git transaction/recovery state machine.
- Do not introduce `materializing`, commit trailers, sidecar recovery files, Git-reset recovery protocols, or pre-approval repo mutation.

Required implementation shape:
- Add a small pure staged-roadmap reader for `agent/staged/roadmap.json`; no free-form backlog parsing.
- If no roadmap file exists, keep current legacy settle behavior. If the file exists but is invalid or the completed task is missing, block fail-closed.
- A valid `successor: null` means end-of-roadmap and settles normally.
- Extend the existing handoff ledger row with staged successor metadata; do not add a new materialization ledger state.
- Extend Planner start with a deferred-handoff entry that accepts successor task id and staged spec while still pinning the current clean repository HEAD and current predecessor `agent/next.md` bytes.
- Refactor normal and deferred Planner start through one common lifecycle so plan/review/remediation behavior stays identical.
- Deferred `_apply_plan()` renders from the staged successor spec, not from the predecessor text, but verifies predecessor text and staged spec digest have not changed before writing.
- The resulting commit is the normal Planner plan commit and is the first repository mutation for the successor.

Acceptance:
- Fixture A COMPLETE + reviewer `next` + roadmap A->B automatically starts B Planner with no new control command and with unchanged HEAD/`agent/next.md` before approval.
- B plan approval produces exactly one new commit; that commit changes `agent/next.md` directly from completed A to B `READY_TO_RUN` plus Approved executable design.
- Repeated daemon ticks/restart do not start a duplicate Planner and do not create a duplicate commit.
- Invalid roadmap/spec blocks without repository mutation; `successor:null` settles normally.
- An already-advertised different `PENDING DESIGN` task continues to use the existing handoff path unchanged.
- Add real roadmap entries `P11x -> P11b -> P11c -> P11d -> null`, with machine-distinct ids and staged specs.
- Full `python -m pytest tests_py -q` and `git diff --check` must pass; commit locally only, no push.

## Approved executable design

Round 2 of the Planner-owned staged handoff plan. It fixes the three problems the reviewer raised. (1) Safety re-check: the deferred apply path reads the raw bytes of agent/next.md and the staged spec and checks their digests. Right after that, and immediately before the only write, it calls read_repository_truth() again. That result must be valid and clean, with branch, HEAD and status_hash all equal to the pinned record. (2) Recovery: the deferred path never uses git reset. If it fails and HEAD has not moved, it writes back the saved predecessor bytes and runs `git add -- agent/next.md` on those bytes. Because the repo was clean and the digest matched, this puts the index back to the HEAD blob. It then checks that the repository is clean again. (3) Task id helper: the plan now names the real one, dev_orchestrator.monitor.telemetry.extract_task_id, which core/transition_executor.py already imports. The rest of the design is unchanged. TransitionExecutor reads agent/staged/roadmap.json and records successor, spec path, raw-byte spec digest and the reviewed branch/HEAD on the existing handoff ledger row. It never changes the repository. ControlCommandCoordinator then calls a new AIPlannerCoordinator.start_deferred(). That call pins the clean HEAD, the raw bytes of the predecessor agent/next.md and the successor spec. Every planner, retry, remediation, review and re-review prompt is built from the successor spec through a single task-source helper. After approval, the apply step alone renders the successor spec as READY_TO_RUN and makes exactly one commit with the existing _commit_plan(). Idempotency reuses source_request_id, the continuation id, handoff_consumed and plan-id reuse.

### Implementation steps
- 1. Add src/dev_orchestrator/core/staged_roadmap.py. It reads files only and makes no git calls. It imports `from dev_orchestrator.monitor.telemetry import extract_task_id`, the same import core/transition_executor.py already uses. It defines a frozen dataclass RoadmapResult(kind, reason, successor_task_id, spec_path, spec_sha256, spec_text), with kind one of 'absent', 'invalid', 'end_of_roadmap' or 'successor'. It also defines read_successor(repo_path, completed_task_id) and two helpers, sha256_bytes(data: bytes) -> str and read_raw(repo: Path, rel_path: str) -> bytes | None, where read_raw returns None on OSError.
- 2. read_successor returns 'absent' only when agent/staged/roadmap.json does not exist. It returns 'invalid' with a reason in these cases: the file cannot be read or parsed as JSON; schema_version != 1; tasks is not a list; an entry has no non-blank task_id; a task_id appears twice; completed_task_id has no entry; only one of successor and successor_spec_path is null; or successor == completed_task_id. If both successor and successor_spec_path are null, it returns 'end_of_roadmap'.
- 3. When successor is not null, successor_spec_path must be a relative POSIX path. It must resolve under <repo>/agent/staged, end in .md, and point to an existing file. Read the file once with Path.read_bytes() into spec_bytes, then require all of the following. spec_bytes contains no b'\r'. It decodes as strict UTF-8. Calling dev_orchestrator.monitor.telemetry.extract_task_id() on the first line starting with '# ' gives exactly the successor id. The text contains 'Status: **PENDING DESIGN**'. The text does not contain '## Approved executable design'. On success, return kind='successor' with spec_sha256=sha256_bytes(spec_bytes) and spec_text=spec_bytes.decode('utf-8').
- 4. In transition_executor.py, find the reviewer-'next' path that settles a COMPLETE task and call read_successor(repo, reviewed_task_id) there. 'absent' keeps the current legacy settle, unchanged. 'invalid' blocks fail-closed with 'staged roadmap invalid: <reason>' and does no repository I/O other than reads. 'end_of_roadmap' settles normally. 'successor' runs only after the existing reviewed repository-truth guard passes. It then calls _record_handoff(..., next_task_id=successor, staged=result, reviewed_branch=truth.branch, reviewed_head=truth.head).
- 5. Give _record_handoff optional keyword arguments staged, reviewed_branch and reviewed_head. When staged is set, also write staged_successor, staged_spec_path, staged_spec_sha256, reviewed_branch and reviewed_head on the row. state='handoff', outcome='planning_required' and the idempotency check on source_request_id stay the same. spec_text is not stored. The existing path for an advertised different PENDING DESIGN task calls _record_handoff without staged and does not change.
- 6. In control_commands.py _resume_decision_handoffs, rows without staged_successor keep the current eligibility check exactly. Rows with staged_successor are eligible only if the advertised telemetry task_id == row['task_id'], next_status contains COMPLETE, and row['staged_successor'] == row['next_task_id']. Other rows are skipped. Eligible staged rows use the same continuation_id and history_path flow. If a plan_id is already in history, call mark_handoff_consumed. Otherwise call self.planner.start_deferred(project, snapshot, continuation_id, row). Handling of blocked and accepted results and of history writes stays the same.
- 7. In ai_planner.py, move the common tail of start() into _begin_lifecycle(project, policy, command_id, task_id, truth, base_fields) -> tuple[str | None, str]. This tail covers resolving the project context, plan_id='ai_plan:'+command_id, the 'planner lifecycle already exists' reuse check, building the record with branch/head/status_hash from truth, the binding save, progress register_project, and starting the thread. start() keeps all its current guards and passes base_fields={'next_text': next_text}. The stored record for normal starts stays the same.
- 8. Add AIPlannerCoordinator.start_deferred(project, snapshot, command_id, handoff). It runs these guards in order and returns (None, reason) on the first failure: port and policy are available; project identity is complete; the handoff has all staged_* fields and reviewed_branch/reviewed_head; read_repository_truth is valid and clean, with branch == reviewed_branch and head == reviewed_head; predecessor_bytes = read_raw(repo, 'agent/next.md') is present and decodes as strict UTF-8; and re-running read_successor(repo, handoff['task_id']) returns 'successor' with the same successor id, spec_path and spec_sha256. Then it calls _begin_lifecycle with task_id=staged_successor and these base_fields: deferred=True, predecessor_task_id, predecessor_next_sha256=sha256_bytes(predecessor_bytes), next_text=predecessor text (kept for audit only), staged_spec_path, staged_spec_sha256 and staged_spec_text.
- 9. Add a static helper _task_source(record) -> (heading, text). For a deferred record it returns a 'Staged successor task spec (<path>; agent/next.md still advertises completed predecessor <id> and must not be used as the task)' heading and staged_spec_text. Otherwise it returns ('Current agent/next.md', next_text). Build the task block in both _planner_prompt (initial, PLANNER_RETRY, PLAN_REMEDIATION) and _review_prompt (initial review and re-review) from _task_source only. Non-deferred prompts must come out identical to today's. _parse_plan keeps comparing against record['task_id'].
- 10. In _apply_plan, keep the current 'applying' state transition and the first repository-truth check. For records where deferred is True, hand off to a new private _apply_deferred_plan(plan_id, record, plan, review_reason, project). Non-deferred records keep the current text-based code path exactly as it is today, including its failure handling.
- 11. _apply_deferred_plan runs its pre-write guards in this order. (a) cur_next = read_raw(repo, 'agent/next.md'). Fail with 'agent/next.md unavailable during plan apply' if it is None, or 'agent/next.md changed during planning' if sha256_bytes(cur_next) != predecessor_next_sha256. (b) cur_spec = read_raw(repo, staged_spec_path). Fail with 'staged spec changed during planning' if it is None or its digest differs. (c) Render updated = _render_next(cur_spec.decode('utf-8'), plan, review_reason). Render failures end as 'plan apply failed: <exc>' with nothing written. (d) As the last step before writing, call read_repository_truth(repo) again. It must be valid and not dirty, with branch == record['branch'], head == record['head'] and status_hash == record['status_hash']. Otherwise fail with 'repository changed during planning'. No other I/O happens between (d) and the write.
- 12. Deferred write and commit: next_path.write_bytes(updated.encode('utf-8')). The rendered text has only LF because the spec has no CR. Then commit = _commit_plan(repo, record['task_id']), which produces 'plan(<successor>): freeze executable design'. The staged spec file is never written.
- 13. Deferred failure recovery, used when the write or the commit raises: read recovery_truth = read_repository_truth(repo). If it is valid and head == record['head'] (no commit was made), write cur_next back with Path.write_bytes(). Then run `git add -- agent/next.md` with hidden_subprocess_kwargs, which sets the index back to the predecessor blob; this works because the repo was clean and the digest matched. Do not use git reset, git restore or git checkout. Read the truth again. If it is not clean with status_hash == record['status_hash'], finish failed with 'plan apply failed: <exc>; repository not restored cleanly'. Otherwise finish failed with 'plan apply failed: <exc>'. If HEAD has already moved or the truth is invalid, change nothing in the repo and finish failed with 'plan apply failed: <exc>'. The existing plan-id reuse prevents a retry.
- 14. After a successful commit, run the existing final-truth check (valid, clean, new HEAD), save the 'ready' state, and emit PLAN_ACCEPTED and NEXT_TASK exactly as today. Share this tail with the non-deferred path through a small private helper, or duplicate it word for word.
- 15. Real roadmap: agent/staged/roadmap.json with P11b.md, P11c.md and P11d.md already exists. Keep it. Add a test that runs read_successor against the real checkout for each link. If a spec fails only the CR check, normalize that file to LF without changing its content.
- 16. Tests: add tests_py/test_staged_roadmap.py. Extend test_transition_executor.py, test_control_commands.py and the planner tests with fake ports and temporary git fixture repos, covering every guard, the prompt source, the final pre-write truth race, reset-free recovery, and the end-to-end and restart behaviour listed under validation.

### Interfaces / contracts
- staged_roadmap.read_successor(repo_path: str | Path, completed_task_id: str) -> RoadmapResult. RoadmapResult is a frozen dataclass: kind Literal['absent','invalid','end_of_roadmap','successor'], reason str|None, successor_task_id str|None, spec_path str|None (repo-relative POSIX), spec_sha256 str|None (lowercase hex SHA-256 of raw bytes), spec_text str|None (strict UTF-8, LF-only).
- staged_roadmap.sha256_bytes(data: bytes) -> str and staged_roadmap.read_raw(repo: Path, rel_path: str) -> bytes | None. All digests are computed over Path.read_bytes() output.
- Task id dependency: dev_orchestrator.monitor.telemetry.extract_task_id(title) -> Optional[str], the existing helper already imported by core/transition_executor.py and adapters/agent_files.py. No new task-id helper is added.
- agent/staged/roadmap.json schema: {"schema_version": 1, "tasks": [{"task_id": str, "successor": str|null, "successor_spec_path": str|null}]}. successor and successor_spec_path are both null or both set. The path must stay under agent/staged/ and end in .md.
- Handoff ledger row (TransitionExecutor executions[source_request_id]): the existing fields stay (task_id=<completed predecessor>, next_task_id=<successor>, state='handoff', outcome='planning_required'). Staged handoffs add staged_successor, staged_spec_path, staged_spec_sha256, reviewed_branch and reviewed_head. handoff_consumed, continuation_id and plan_id are still set by the existing mark_handoff_consumed. No new ledger states.
- AIPlannerCoordinator.start_deferred(project: dict, snapshot: dict, command_id: str, handoff: dict) -> tuple[str|None, str]. It follows the same contract as start(): (plan_id, 'planning started' | 'planner lifecycle already exists') or (None, reason). Failure reasons: 'staged handoff metadata incomplete', 'planner requires a clean repository', 'repository moved since review', 'agent/next.md unavailable', 'staged spec changed since handoff', 'staged roadmap invalid: <reason>'.
- Deferred plan record: the normal fields (task_id=<successor>, branch, head, status_hash pinned at start, plan_id='ai_plan:'+continuation_id) plus deferred=True, predecessor_task_id, predecessor_next_sha256, next_text (audit only), staged_spec_path, staged_spec_sha256 and staged_spec_text.
- AIPlannerCoordinator._task_source(record) -> tuple[str, str] is the only source of task text for _planner_prompt (initial, PLANNER_RETRY, PLAN_REMEDIATION) and _review_prompt (initial, post-remediation).
- Deferred apply guard order, all checked before the single write: initial truth (valid, clean, branch/head/status_hash) -> raw next.md digest == predecessor_next_sha256 -> raw staged spec digest == staged_spec_sha256 -> render -> final truth re-read (valid, clean, branch/head/status_hash unchanged) -> write_bytes(agent/next.md) -> _commit_plan(repo, successor). Failure reasons: 'repository changed during planning', 'agent/next.md unavailable during plan apply', 'agent/next.md changed during planning', 'staged spec changed during planning', 'plan apply failed: <exc>[; repository not restored cleanly]'.
- Deferred recovery contract: repository changes happen only if HEAD == record head. Recovery consists of writing back the predecessor bytes plus `git add -- agent/next.md`. It never calls git reset, restore or checkout. The staged spec file is never written.

### Risks / failure modes
- TOCTOU between the final truth read and the write. Mitigation: the truth re-read, checking valid, clean and branch/HEAD/status_hash, is the last operation before write_bytes. After the commit, the existing final-truth check confirms a clean new HEAD. The remaining window is limited to the gap between that re-read and the write, which is the same as the existing Planner apply.
- Recovery re-stage relies on the index matching HEAD before the write. Mitigation: recovery runs only when the repo was clean with the same status_hash right before the write and HEAD has not moved. A second truth read confirms the restore, and any leftover difference is reported as 'repository not restored cleanly' instead of being hidden.
- Prompt drift between normal and deferred planning. Mitigation: a single _task_source, a single _begin_lifecycle, and prompt tests for every planner, retry, remediation and review path.
- Relaxed advertised-task check for staged rows. Mitigation: require that the advertised task is the row's predecessor with COMPLETE status, and pin clean HEAD == reviewed_head at start and again at apply.
- A crash between _commit_plan and the ready-state save leaves the record in 'applying' with HEAD advanced. Mitigation: plan-id reuse blocks a second planner, and any re-apply fails the HEAD guard, so no second commit is possible. No new recovery state machine is added, per the owner.
- Importing monitor.telemetry from core. Mitigation: core/transition_executor.py already uses this exact import, so staged_roadmap adds no new layering dependency.

### Out of scope
- Any repository change by TransitionExecutor or ControlCommandCoordinator (commits, agent/next.md edits, staged spec edits).
- New ledger states such as materializing, commit trailers, sidecar recovery files, or Git-reset/restore/checkout recovery protocols in the deferred path.
- Changing the existing non-deferred start(), _apply_plan text comparison, prompt content or failure handling.
- Free-form backlog parsing or any roadmap source other than agent/staged/roadmap.json.
- Implementing P11b, P11c or P11d, or editing their spec content beyond LF normalization if needed.
- Worker launch behaviour, reviewer decision policy, and the existing different-task PENDING DESIGN handoff path.
- Pushing to a remote or opening a PR.
