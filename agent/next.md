# P16.10 - Automatic Failure Harvesting & Regression Promotion

Status: **READY_TO_RUN**

## Goal

Convert unattended-execution anomalies and control-only owner interventions into durable incident families and validated regression candidates automatically.

## Problems to close

1. Unattended-execution anomalies (such as watchdog execution loss, transient worker failures, launch gaps, or recovery handoffs) often require manual inspection or ad-hoc debugging to understand failure patterns.
2. Manual `continue`, `retry`, `reconcile`, or restart interventions that supply no new owner information but restore forward progress are symptoms of unhandled or incomplete recovery. These control-only interventions should be automatically recorded as first-class quality metrics and incident signals.
3. Incidents must be fingerprinted and deduplicated so recurring anomalies strengthen an existing incident family rather than generating noise or duplicate records.
4. Candidate regression fixtures and tests should be synthesized from incident evidence automatically, but must remain staged outside the permanent regression suite until reproduction, discrimination, stability, and independent review gates pass.

## Requirements & Scope

- Treat any `continue`, `retry`, `reconcile`, or restart command that supplies no new owner information (such as identical parameters/HEAD) but restores progress as an incident signal (`CONTROL_ONLY_INTERVENTION`).
- Capture authoritative before/after lifecycle, execution, review, broker, watchdog, Git/HEAD, and recovery evidence in restart-safe incident packets (`runtime/incident-packets/`).
- Compute stable semantic failure fingerprints over normalized failure causes, lifecycle transitions, and diagnostic evidence to deduplicate recurring failures.
- Generate candidate deterministic fixtures/tests automatically, keeping candidate tests isolated in a staging area (e.g. `tests_candidate/`) until automated reproduction, discrimination, and independent review gates approve promotion to `tests_py/`.
- Use ProgressObligation and execution lineage contracts to distinguish legal waiting/startup grace from silent stalls or execution loss.
- Make task-level activity evidence a watchdog input: daemon/monitor/summary heartbeat writes prove only `SYSTEM_ALIVE` and MUST NOT refresh task progress. Planner/Reviewer/Worker output growth, broker/request state transitions, execution-lineage changes, lifecycle transitions, progress milestones, and Git/HEAD changes are task evidence.
- Track `last_task_activity_at` separately from `last_meaningful_progress_at`; repeated `STALL_DETECTED`, identical diagnostics/owner gates, watchdog self-writes, and heartbeat-only file churn MUST NOT count as meaningful progress.
- If the daemon continues ticking but no Planner/Reviewer/Worker is alive and no task-level activity occurs within the bounded ProgressObligation window, classify `ORCHESTRATOR_ALIVE_TASK_STALLED`, capture it as a P16.10 incident, and enter bounded recovery rather than reporting the task as running.
- Add a regression reproducing the 2026-09-25 P16.10 false-running case: daemon heartbeat remains healthy while lifecycle is `REVIEW_FAILED`/`OWNER_GATE`, worker is not alive, and task evidence is stale; watchdog must report stalled and attempt/route safe recovery.
- Track manual `CONTROL_ONLY` interventions as an explicit metric; target zero control-only interventions for standard lifecycle paths.
- Safety boundaries: Never auto-merge production fixes, weaken owner/safety/Git gates, or actuate real physical hardware as part of candidate regression generation.

## Sequence

P16.7 self-healing activation -> P16.8 golden-path liveness -> P16.9 execution-loss watchdog -> P16.10 automatic failure harvesting -> P16.11 AGY-first resource routing -> P16.12 Web Sol persistent pairing and truthful availability.

## Approved executable design

Implement bounded automatic failure harvesting, semantic incident deduplication, staged regression synthesis, task-level liveness detection, and operator-invoked promotion. Promotion uses an immutable pre-review digest over candidate content and the five executable gates only; independent review binds to that digest, while the final six-gate decision is derived separately and never changes the reviewed digest. Preserve owner, Git, recovery, and hardware safety boundaries, and keep all daemon integrations fail-closed and additive.

### Implementation steps
- Create src/dev_orchestrator/incidents/ with the incident store, capture, fingerprint, harvesting, attribution, obligations, role liveness, owner-gate, candidate, review, regression-owner, and promotion modules. Keep existing subsystem changes to thin guarded integrations; incident failures must not abort daemon ticks or alter P16.7-P16.9 behavior.
- Store runtime data beneath runtime/incident-packets/: index.json with schema_version, revision, last_txn_id, families and candidate pointers; immutable packet files; candidate manifests, sources, executable-gate snapshots and reviews; journal intents; orphaned payloads; and an incidents.lock using the existing InterProcessFileLock. Corrupt or future-schema indexes are quarantined and loaded as degraded empty state without raising through daemon paths.
- Implement journaled mutations with one atomic index.json write as the commit point. Under the store lock, write an intent containing operation, payload hashes, prior revision and target revision; write immutable side files; atomically write the target index with last_txn_id and target revision; then mark and remove the intent.
- Reconcile unfinished intents at store open and harvest start. Treat matching last_txn_id or target revision as committed; reapply only when the live revision equals the recorded prior revision and payload hashes verify; otherwise orphan a superseded transaction or unverifiable payload. Reconciliation must preserve newer state and reach a fixed point.
- Keep packets append-only. A repeated semantic fingerprint updates the family recurrence count and bounded evidence-reference list without creating another packet or candidate. Retention drops only excess references, records dropped_evidence_count, and never deletes incident, candidate, review, or gate-snapshot files.
- Implement incident_fingerprint over canonical JSON restricted to normalized failure class, diagnosis or blocker code, lifecycle and contract class, role and broker state classes, Git-anchor relation, continuation relation, and invariant identifier. Reject volatile or identifying keys such as timestamps, ages, UUIDs, PIDs, and absolute paths.
- Capture restart-safe packets containing authoritative lifecycle, execution intent/context and lineage, planner/reviewer/broker/watchdog state, Git anchors, recovery epoch, progress obligation, role-liveness verdicts, owner-gate resolution, attribution, bounded evidence references, observation/inference/unknown separation, and before/after transitions. Do not persist chain-of-thought or raw transcripts.
- Expose latest_owner_gate and add a fail-closed owner-gate authority resolver combining watchdog/planner gates, project_identity and OwnerControlStore state. Classification and recovery require resolved authority, no pending gate, no pause, and unchanged gate_id and recovery_epoch_id both at detection and immediately before enqueue. Pending or unknown authority yields observation-only OWNER_GATE_WAIT.
- Add three-role liveness resolution. Worker evidence reuses execution-lineage and transition-executor liveness; Planner and Reviewer each use injected coordinator-thread state, durable role ledgers, AIBroker request state, and bounded provider-output freshness. A role is dead only when every required source is readable and negative; any unavailable source produces unknown.
- Require Planner, Reviewer, and Worker all to be dead before ORCHESTRATOR_ALIVE_TASK_STALLED. Any alive or unknown role blocks classification and recovery; persistent unknown state may emit one deduplicated OWNER_GATE after the existing escalation window.
- Resolve ProgressObligation for REVIEWING, REVIEW_FAILED or REMEDIATE_READY, READY_TO_RUN or NEXT_TASK_READY, and EXECUTING states, including expected event, successor action, evidence source, deadline or tick budget, recovery eligibility, escalation, and legal-wait status. Declared external waits, startup grace, pauses, and pending owner gates are never stalls.
- Separate last_task_activity_at from last_meaningful_progress_at. Planner/Reviewer/Worker output growth, broker transitions, execution-lineage and lifecycle transitions, non-watchdog milestones, and Git/HEAD changes are task evidence. Heartbeats, status mirrors, watchdog writes, incident writes, repeated STALL_DETECTED, identical diagnostics, and repeated owner gates cannot refresh meaningful progress.
- Add incident runtime paths to watchdog-owned and activity-evidence exclusions so harvesting cannot manufacture activity or recursively trigger incidents. Preserve clock-free fingerprint validation for all new semantic payloads.
- Add orchestrator_alive_task_stalled to diagnostics and route it through existing bounded recovery budgets, cooldowns, recovery epochs, and wd- command identity. Classify only with a fresh daemon tick, all roles dead, a stale unsatisfied non-legal ProgressObligation, stale task evidence, and resolved absence of an owner gate; never report that state as running.
- Call harvest_tick once after watchdog and supervisor advancement in each daemon tick, guarded so harvesting failure becomes diagnostic evidence and a no-op. Derive anomalies from durable subsystem records rather than invasive instrumentation.
- Provide individually testable detectors for watchdog recovery, actionable execution loss, unconsumed planner/reviewer results, launch gaps, restart/reconcile outcome changes, recovery-cycle exhaustion or livelock, control-only intervention, and orchestrator-alive-task-stalled. Use durable source-record identities as occurrence keys.
- Persist the pre-command project_identity in command outcomes. Classify continue, retry, rereview, reconcile, or restart as CONTROL_ONLY only when no parameters, HEAD, gate decision, or technical information changed and later durable evidence proves restored progress; classify stop/pause as EXPLICIT_STOP and real decisions or changed inputs as NEW_INFORMATION.
- Generate candidate manifests and deterministic synthetic test sources in the runtime store only. Record preconditions, trigger sequence, invariant, invalid outcome, fixture and oracle descriptions, source incidents, generated_by, candidate_content_sha256, and failing/corrected fixture anchors. Candidate execution must not use live Web, RDC, SSH, providers, or hardware.
- Resolve a single configured regression_owner repository for all P16.10 defects; affected project repositories are evidence only and never destinations. Permit inference only when the repository containing dev_orchestrator matches exactly one configured project. Before any materialization or promotion, verify repository truth, pyproject project identity, src/dev_orchestrator/__init__.py, and the configured tests root.
- Materialize candidates only into the verified owner's git-excluded tests_candidate directory, adding the path to .git/info/exclude before writing. Install a staging conftest that ignores all candidate tests unless DEVORCH_CANDIDATE_TESTS=1, so normal repository and tests_py runs do not collect them.
- Persist each executable evaluation as an immutable snapshot containing candidate_content_sha256 and normalized results plus decisive evidence hashes for reproduction, discrimination, stability, isolation, and deduplication. Compute pre_review_digest solely from a schema/version identifier, candidate content hash, and canonical five-gate snapshot; exclude review state, candidate lifecycle state, run IDs, timestamps, and other volatile metadata.
- Allow record_candidate_review only when a current five-gate snapshot exists. Store reviewer identity, verdict, notes, candidate_content_sha256, and pre_review_digest through the incident transaction protocol. Resolve acceptance only when the current content and five-gate digest still match and reviewer_id differs from generated_by; recording or resolving review must never rewrite the executable snapshot or its digest.
- Derive the final promotion state from the unchanged five executable results plus resolve_candidate_review as the sixth gate. A separate promotion_decision_digest may cover pre_review_digest, review_id, and verdict for audit, but it must not replace or feed back into pre_review_digest. An identical deterministic reevaluation retains review validity; candidate changes or material changes to any executable gate snapshot make the review stale.
- Make promotion operator-invoked and destination-free. Under candidate-store locking, revalidate the current content hash, pre_review_digest, five passed executable gates, accepted independent review, clean verified owner repository, expected branch/HEAD, and create-new destination. Never overwrite, stage, or commit. On post-write failure, remove the new file, verify restoration by status_hash, and emit an OWNER_GATE plus block further promotion if residue remains.

### Interfaces / contracts
- incidents/__init__.py exports harvest_tick, capture_incident, incident_fingerprint, classify_owner_action, resolve_progress_obligation, resolve_owner_gate_authority, resolve_role_liveness, resolve_regression_owner, generate_candidate, materialize_candidate, evaluate_promotion, record_candidate_review, resolve_candidate_review, resolve_promotion_state, promote_candidate, load_incident_store, and resolve_incident_policy.
- incidents/store.py provides load_incident_store, begin_txn, commit_txn, reconcile_journal, and index_revision. index.json revision and last_txn_id are authoritative; the atomic index write is the sole commit point.
- Reconciliation outcomes are committed_confirmed, reapplied, superseded_txn, and payload_unverified, corresponding to crash-after-commit, crash-before-commit, lost race, and unverifiable payload.
- capture_incident(runtime_root, project_id, task_id, classification, semantic, evidence, occurrence_key) returns the incident family and is idempotent for a fingerprint and occurrence-key pair.
- incident_fingerprint(semantic) returns a stable truncated SHA-256 value and rejects unallowlisted or volatile fields.
- resolve_owner_gate_authority(runtime_root, snapshot) returns resolved, pending, gate_id, gate_source, paused, and reason; unresolved authority implies pending. control.surface.latest_owner_gate becomes the public source shared with project_identity.
- resolve_role_liveness(runtime_root, project_id, snapshot, planner, reviewer, executor, policy, now) returns worker, planner, and reviewer evidence rows plus all_dead and any_unknown. Coordinator has_live_role(project_id) returns true, false, or None.
- resolve_progress_obligation(snapshot, context, policy) returns state, expected_event, successor_action, evidence_source, deadline_at or tick_budget, timeout_classification, auto_recovery_allowed, escalation, and legal_wait.
- harvest_tick(runtime_root, config, summary, executor, watchdog, planner, reviewer, now) returns captured incident rows and uses a named DETECTORS registry for every required anomaly source.
- classify_owner_action(action, command_record, before, after) returns NEW_INFORMATION, CONTROL_ONLY, or EXPLICIT_STOP. Command outcomes add an immutable pre-command identity snapshot.
- resolve_regression_owner(config) returns project_id, repo_path, tests_root, candidates_root, verified, and reason. No candidate API accepts an affected-repository or caller-supplied destination.
- generate_candidate stores a runtime-only candidate with generated_by and candidate_content_sha256; materialize_candidate writes only to the verified owner's ignored candidates_root.
- evaluate_promotion(runtime_root, candidate_id, runner) executes and persists only the five executable gate results, computes pre_review_digest, and returns executable_gates, pre_review_digest, review_gate, promotable, and promotion_decision_digest. Review status is derived after persistence and is excluded from pre_review_digest.
- compute_pre_review_digest(candidate_content_sha256, executable_gates, schema_version) canonicalizes only the candidate hash and reproduction, discrimination, stability, isolation, and deduplication snapshots, including stable evidence hashes but excluding timestamps and review data.
- record_candidate_review(runtime_root, candidate_id, reviewer_id, verdict, notes) binds the review to candidate_content_sha256 and pre_review_digest. resolve_candidate_review returns accepted, stale, review_id, reviewer_id, and reason without mutating the executable snapshot.
- resolve_promotion_state(runtime_root, candidate_id) derives five executable gate verdicts plus the independent-review verdict and optional promotion_decision_digest. It never modifies pre_review_digest.
- promote_candidate(runtime_root, candidate_id, config_path, expected_head, expected_branch) accepts no destination or review argument and refuses with stable codes for unverified owner, incomplete or stale executable gates, missing/stale/non-independent review, invalid or dirty repository, anchor mismatch, collision, or failed rollback.
- Watchdog and telemetry additions are additive: StallAssessment gains last_task_activity_at, last_meaningful_progress_at, progress_obligation, role_liveness, and stall_classification; status gains system_alive, task_active, task_progressing, and incident metrics; no existing key is removed or renamed.
- CLI adds incident-list, incident-show, candidate-list, candidate-evaluate, candidate-review, candidate-materialize, and candidate-promote. Candidate evaluation establishes the stable pre-review snapshot; review and promotion consume it without folding review into its digest.

### Risks / failure modes
- A journal crash could be misclassified as committed or uncommitted; authoritative index revision and last_txn_id markers plus four reconciliation-path tests mitigate duplication and loss.
- A stale intent could overwrite newer state; reapply is permitted only from its exact prior revision, while all other live revisions cause orphaning.
- Incident writes could create artificial progress or recursive incidents; explicit runtime exclusions and heartbeat-versus-task evidence tests prevent feedback.
- Role evidence could falsely declare a stalled task while Planner or Reviewer remains active; all three roles must be provably dead, and any unreadable source fails closed to unknown.
- Owner-gate ambiguity could bypass a real owner decision; authority is resolved twice with unchanged gate and recovery epoch identity before recovery enqueue.
- Separating task activity from meaningful progress could make stall timing too aggressive; legal waits and startup grace remain explicit, and existing watchdog suites provide regression coverage.
- A control command could be mislabeled CONTROL_ONLY before its effect is known; classification waits for durable post-command progress and compares it with the persisted pre-command identity.
- Fingerprint fields could over-deduplicate unrelated failures or fragment recurrences; an allowlisted semantic contract and detector-specific fixtures constrain normalization.
- Regression candidates could dirty or target the wrong repository; runtime-only generation, one verified regression owner, ignored materialization, and destination-free APIs contain writes.
- The independent-review gate could become circular if review state enters the reviewed digest; pre_review_digest explicitly contains only candidate content and five executable gates, while the sixth gate and promotion_decision_digest are derived separately.
- An unchanged reevaluation could spuriously invalidate review if volatile metadata enters the digest; canonical digest inputs exclude run IDs, timestamps, lifecycle state, and review data.
- A materially changed evaluator could reuse an old review; evaluator schema and stable policy identity are included in the executable snapshot so semantic changes produce a new pre_review_digest.
- Concurrent candidate edits or promotion attempts could defeat preconditions; store locking, immutable snapshots, immediate content rehashing, create-new writes, and Git anchor revalidation reduce TOCTOU exposure.
- A failed promotion rollback could leave the owner repository dirty; status-hash verification, explicit residual-path escalation, and a durable promotion block require owner cleanup before retry.

### Out of scope
- Writing candidates or promoted tests into any repository other than the verified DevOrchestrator regression-owner repository.
- Automatically staging, committing, merging, or applying production fixes; successful promotion creates only one uncommitted new regression-test file.
- Weakening owner, safety, permission, Git, repository-cleanliness, or physical interlock gates.
- Checking out, resetting, stashing, or otherwise mutating repository history during generation or evaluation.
- Driving live Web, browser, RDC, SSH, provider, or physical-hardware sessions from candidate tests.
- Persisting model chain-of-thought or raw prompt/response transcripts.
- Daemon-initiated review recording, materialization, or promotion; these operations remain explicit operator actions.
- Deleting incident packets, candidates, gate snapshots, or reviews as a retention mechanism.
- Redesigning P16.9 execution-loss policy, recovery budgets, coordinator lifecycles, or existing progress-fingerprint semantics beyond the additive P16.10 integrations.
- Building a new web or mobile UI; existing CLI, status, and reporting surfaces receive additive fields only.
- P16.11 AGY-first resource routing and P16.12 Web Sol persistent pairing or truthful availability.
- Migrating historical runtime artifacts other than bounded compatibility handling for existing P16.7-P16.9 fixtures.
