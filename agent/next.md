# P16.12 Web Sol Persistent Pairing & Truthful Availability

Status: **COMPLETE**

Goal: make Web Sol a restart-safe AI resource that normally requires only one manual pairing, automatically restores service after Chrome/Tampermonkey/DevO restarts, and never reports AVAILABLE/LIVE from partial transport health.

## Problems to close

1. The ChatGPT userscript can show `LIVE` when the 8765 claim bridge is reachable even if the independent 8770 control heartbeat is stale or absent.
2. Heartbeat capability loss/expiry currently can require a manual `Pair DevOrchestrator 8770 heartbeat` recovery, despite the capability being stored in Tampermonkey.
3. Browser, userscript, bridge, control service, conversation binding and end-to-end inference health are not represented as one authoritative availability state.
4. A healthy port or heartbeat alone does not prove that DevO can enqueue a request, have the browser claim it, receive a Web Sol response and acknowledge/consume it.

## Requirements & Scope

- Normal lifecycle is **pair once, recover automatically** across Chrome/Tampermonkey and DevO service restarts.
- Persist or safely renew/recover the heartbeat capability. Require owner re-pairing only when credentials are truly unrecoverable/revoked or security policy requires it.
- Separate and expose at least: bridge reachability, browser claim presence, control heartbeat, binding identity, capability validity, and end-to-end probe status.
- Replace misleading `LIVE` semantics: browser UI must show `DEGRADED/OFFLINE` when heartbeat/control health is stale even if 8765 claim polling succeeds.
- DevO resource routing must not mark Web Sol `AVAILABLE` from a single signal. Availability requires fresh browser presence + fresh control heartbeat and, after startup/recovery, a successful bounded end-to-end probe.
- Implement a lightweight deterministic probe covering `enqueue -> browser claim -> ChatGPT/Web Sol response -> Bridge acknowledge/consume`, with timeout and failure classification.
- Automatically retry/recover bounded transient failures; integrate unrecoverable/repeated failures with P16.10 incident harvesting and resource failover.
- Detect duplicate/stale tabs and stale bindings without allowing them to create false availability.
- Record timestamps and reason codes so the scheduler can distinguish `AVAILABLE`, `DEGRADED`, `OFFLINE`, `PAIRING_REQUIRED`, and `PROBE_FAILED`.
- Do not fabricate heartbeat/presence or synthetic success merely to satisfy health checks.

## Acceptance

1. After one successful pairing, restart Chrome and restart DevO services independently; Web Sol returns to AVAILABLE without manual pairing in normal cases.
2. Kill or invalidate the 8770 heartbeat path while leaving 8765 healthy; UI and scheduler stop reporting LIVE/AVAILABLE within the defined freshness window.
3. Startup/recovery runs a bounded real end-to-end probe and only marks Web Sol AVAILABLE after the probe succeeds.
4. Expired/revoked/unrecoverable capability produces explicit PAIRING_REQUIRED rather than false LIVE or an infinite retry loop.
5. Duplicate/stale ChatGPT tabs do not cause false availability or route requests to the wrong conversation.
6. Automated tests cover capability persistence/recovery, split-brain 8765/8770 health, stale heartbeat, stale binding, probe timeout/failure, and successful restart recovery.

Sequence: P16.10 automatic failure harvesting -> P16.11 AGY-first pool benchmark and evidence-based routing -> P16.12 Web Sol persistent pairing and truthful availability.

## Approved executable design

Make Web Sol restart-safe after one pairing and establish one authoritative per-binding availability contract across the 8765 bridge, 8770 control service, browser presence, binding identity, capability state and real inference probes. Add a durable, convergent cancellation protocol for stalled submitted work, expose the authoritative state to the userscript so local partial health can never promote LIVE, and distinguish retryable capability-store outages from authoritative revoked or unknown credentials so transient failures never erase the persisted token.

### Implementation steps
- Add `core/websol_health.py` with per-`(project_id, adapter, binding_id)` signal and availability models for AVAILABLE, DEGRADED, OFFLINE, PAIRING_REQUIRED and PROBE_FAILED. Persist evaluated entries, reason codes, timestamps, probe generation and failover summary in versioned `runtime/websol-health.json` using atomic writes and `InterProcessFileLock`; unreadable, stale, missing or unknown-version entries are never AVAILABLE.
- Collect six independent signals: a bounded loopback HTTP `GET /v1/health` against the address in `runtime/bridge.json`, exact binding claim presence from `BrowserBridgeStore.binding_status()`, control heartbeat freshness and live-tab count, configured-versus-runtime binding identity, capability verdict for each live tab, and the current probe generation. Keep the listener test independent from bridge presence and make clocks/probers injectable.
- Implement deterministic fail-closed evaluation. AVAILABLE requires every signal healthy and a successful current-generation probe; listener failure or absent claim presence is OFFLINE; authoritative revoked/unknown capability is PAIRING_REQUIRED; failed current probe is PROBE_FAILED; duplicate tabs, stale heartbeat, mismatched binding, legacy unverified capability or retryable capability-store unavailability are DEGRADED. Missing or stale evidence cannot promote availability.
- Replace security reads that collapse canonical-store errors to an empty capability set. Introduce structured capability verdicts `valid`, `revoked`, `unknown` and `unavailable`: only a successfully read authoritative store may return revoked/unknown, while I/O, malformed data, unsupported schema and lock/service failures return unavailable. Mutations must refuse to overwrite unreadable canonical state.
- Persist the authenticated capability identity on each accepted session heartbeat. Extend session and per-tab records with stable `capability_pairing_id`, source and verification time, prune/count stale tabs, and treat legacy records without identity as unverified until refreshed. Owner-master heartbeats remain valid with an explicit owner source.
- Add strict capability inspection and renewal operations. Heartbeat authentication returns 503 with `capability_store_unavailable` for retryable canonical-store failures, 401 with distinct revoked/unknown reason codes for authoritative failures, and 200 with the stable pairing identity when valid. Rotate session-heartbeat tokens under the canonical lock while preserving `pairing_id` and a bounded previous-token grace period; never renew revoked credentials.
- Make `runtime/websol-health.json` the only state allowed to promote the browser badge. Include the exact current binding's serialized health entry and `valid_until` in successful heartbeat responses, selected only when that binding is currently owned by a project; expose the same entries through an owner-authenticated health endpoint for dashboard and CLI consumers. Missing, wrong-key or expired health snapshots are explicitly non-LIVE.
- Update the userscript capability storage to a record containing token, pairing id and timing metadata, migrating the existing token-only value after the first successful heartbeat. Preserve it on transport errors, timeouts, 5xx and `capability_store_unavailable`; retry with bounded backoff and renewal. Clear it only for authoritative revoked/unknown verdicts or explicit user action.
- Refactor userscript badge calculation into a pure function that consumes the authoritative health snapshot plus local bridge/control observations. It may demote AVAILABLE because of a failed local bridge poll, stale heartbeat, duplicate-tab response or expired snapshot, but local evidence can never promote LIVE. Route idle, 204, response-acknowledged and recovery paths through this function; CLAIMED/WAITING remain activity details and do not mask DEGRADED/OFFLINE resource state.
- Add a bounded real probe using a reserved request-id prefix and nonce: enqueue to the exact binding, observe claim and response, verify the exact response marker and nonce, acknowledge, then discard the probe record. Classify not-bound, no-claim, response timeout, malformed response, acknowledgement failure and transport failure; invalidate probe generation on daemon restart, pairing change, rebinding or loss of prerequisite health.
- Isolate probes from workflow decisions: make the Response Consumer skip reserved probe records and add an exact-identity probe discard operation that refuses non-probe ids. Persist exponential probe backoff and a hard attempt cap so steady-state ticks do not enqueue repeated probes or fabricate success.
- Extend bridge records with `first_claimed_at`, a hard `claim_deadline_at` and durable cancellation fields. Clamp every claim and renewal lease to a configurable maximum total claim lifetime aligned with the userscript wait deadline; after that deadline the request cannot be renewed or reclaimed and is eligible for failover even if general binding health still appears healthy.
- Replace the non-convergent live-claim withdrawal behavior with explicit revocation. Under the queue lock, withdrawing pending work finalizes a durable withdrawn tombstone; withdrawing an active claim atomically sets `cancel_requested_at` and `cancel_deadline` and returns `revocation_pending`. A cancellation-marked record is never reclaimed, `renew()` rejects it immediately, and `respond()` may win only until the already-issued capped lease expires. A later idempotent withdrawal finalizes the tombstone, giving cancellation a convergence bound of at most one remaining lease.
- Add occurrence-level failover decisions for prepared/unbound work, unhealthy submitted work and submitted work whose response/maximum-claim deadline expired. Before submission, fail over after the configured grace directly; after submission, first obtain finalized withdrawal. `revocation_pending` is reconciled until response-wins or the fixed deadline, never reset by claim renewal or reclaim; responded work cancels failover and continues through the normal consumer.
- Persist failover intent in versioned `runtime/websol-failover.json`, keyed by `(project_id, run_id)` and containing the frozen request identity, binding, routing evidence, withdrawal/cancellation state, attempts and timestamps. Reconcile idempotently at startup and every tick: intent -> cancellation requested/finalized -> dispatcher marked -> exact reviewer submitted -> terminal. Cap attempts and emit an unavailable result rather than retrying forever.
- Add `AIReviewerCoordinator.submit_failover_review(project_id, run_id, failover_record_id, policy)` using `ai_review:<run_id>` as the at-most-once identity and the exact completed AIBroker transition for that occurrence. Do not use AGY pool acquisition for this path; persist requested routing inputs first and attach the actual execution `ResourceContext` as evidence after completion.
- Extend dispatcher occurrences with additive failover fields and a backward-compatible ledger version. Delivery requires authoritative AVAILABLE for the exact project/binding when an availability provider is supplied; absent provider preserves existing behavior. A finalized failover permanently blocks subsequent Web Sol submission, a response permanently blocks failover, and frozen request identity is never regenerated.
- Wire a Web Sol coordinator into the daemon tick with exception isolation: collect/evaluate/persist health, reconcile cancellation and failover, gate dispatch, consume responses, and schedule probes only when prerequisites permit. Share the health store with the control HTTP server so heartbeat responses, scheduler decisions, dashboard and CLI all read the same per-binding entry.
- Emit deduplicated P16.10 incidents for PAIRING_REQUIRED transitions, repeated PROBE_FAILED, capability-store unavailability beyond its retry threshold, failover unavailable and failover attempt exhaustion. Add CLI/dashboard presentation of per-binding state, six signals, reason timestamps, probe generation and failover/cancellation state.
- Document the availability precedence, authoritative-browser-state rule, four capability verdicts, bounded claim/cancellation state machine, probe isolation and exact-occurrence failover invariants. Add focused health, security recovery, userscript, probe, cancellation, failover, daemon and restart tests while leaving safe local naming and exception details to implementation and Technical Review.

### Interfaces / contracts
- `core/websol_health.py`: `WebSolAvailability`, frozen `WebSolSignal` and `WebSolHealth`; `health_key(project_id, adapter, binding_id)`; `probe_bridge_listener(...)`; `collect_websol_signals(...)`; and pure `evaluate_websol_availability(...)`. Fixed signal names are `bridge_listener`, `browser_claim_presence`, `control_heartbeat`, `binding_identity`, `capability` and `probe`.
- `WebSolHealthStore(runtime_root)`: `get`, `put`, `list_all`, `record_probe`, `invalidate_generation` and probe-backoff accessors over versioned `runtime/websol-health.json`. Entries carry `evaluated_at` and `valid_until`; invalid or expired data is non-AVAILABLE.
- `control/security.py`: `CapabilityVerdict` with valid|revoked|unknown|unavailable; `capability_state(pairing_id)`, `capability_status(header)`, `capability_identity(header)` and `renew_session_capability(header)`. Canonical-store unavailability is distinct from an authoritative absent credential and all mutation paths fail closed on unreadable state.
- `control/store.py`: `heartbeat(..., capability_id=None, capability_source="capability")` stores identity per session and tab; `session_status()` and `list_sessions()` expose active/stale tab counts and capability metadata while retaining existing fields.
- Control HTTP: heartbeat 200 data includes `{session, websol_health}` for the exact currently bound adapter/binding; retryable security-store failure returns 503 `capability_store_unavailable`; authoritative credential failures return reason-coded 401. Add capability renewal and owner-authenticated per-binding Web Sol health endpoints with appropriate loopback/CORS handling.
- Userscript test API: `computeAdapterState(input) -> {state, detail}`, `classifyHeartbeatResult(status, body)` and capability record migration helpers. LIVE is possible only for an exact, unexpired authoritative AVAILABLE snapshot; bridge/control/capability observations are demotion-only.
- `core/websol_probe.py`: reserved probe prefix, frozen `ProbeResult`, and `run_websol_probe(...)` with a caller-supplied deadline and classified failure. `BrowserBridgeStore.discard_probe(...)` accepts only exact reserved probe identities.
- `bridge/store.py`: `withdraw(adapter, binding_id, request_id, nonce, reason, now=None) -> WithdrawResult` with outcomes withdrawn|revocation_pending|responded|missing. Claims expose a hard deadline; cancelled claims reject renewal, cannot be reclaimed, accept a response only within the pre-cancellation lease, and finalize idempotently after its deadline.
- `core/websol_failover.py`: pure failover decision enum/function, `WebSolFailoverStore`, and `FailoverEngine.advance/reconcile`. A submitted occurrence cannot reach reviewer submission until bridge withdrawal is final; `revocation_pending` has a fixed persisted deadline and never restarts its wait window.
- `core/ai_reviewer.py`: `submit_failover_review(*, project_id, run_id, failover_record_id, policy=None) -> str | None`, anchored to `ai_review:<run_id>` and the exact source transition. Existing `advance()` and enabled-project behavior remain compatible.
- `core/dispatcher.py`: optional availability provider keyed by `(project_id, adapter, binding_id)` and additive occurrence fields `failover_state`, `failover_reason`, `failover_decided_at` and `failover_record_id`, with backward-compatible ledger loading.
- CLI/dashboard: per-binding health display and a bounded probe trigger/readout; daemon/control server share the same health-store instance or equivalent locked persisted source, so no consumer independently invents AVAILABLE.

### Validation plan
- Cancellation convergence: submit and claim a request, repeatedly attempt renewal/reclaim while failover requests withdrawal, and prove the first withdrawal persists `revocation_pending`, renewal is rejected, reclaim never returns the record, and final withdrawal succeeds no later than the original capped lease deadline.
- Response race: if an exact response arrives before the cancellation deadline it wins and no reviewer is launched; after the deadline or finalized withdrawal, `respond()` raises `BridgeConflictError`. Reopen the store between each phase and verify the same outcome and deadline survive restart.
- Maximum lifetime: repeated successful renewals cannot extend authority past `claim_deadline_at`; after the deadline neither renewal nor reclaim can keep `claim_active`, and reconcile converges to one finalized withdrawal and at most one failover review.
- Authoritative badge: with fresh local 8765 polling and heartbeat but authoritative states DEGRADED, OFFLINE, PAIRING_REQUIRED or PROBE_FAILED, the userscript never displays LIVE. Missing, stale, wrong-binding and malformed snapshots are also non-LIVE; only an exact unexpired AVAILABLE entry can promote it.
- Immediate conservative demotion: a heartbeat response reporting duplicate live tabs, a mismatched current binding, unavailable capability store or an expired health snapshot demotes the badge even if its previously cached authoritative state was AVAILABLE.
- Capability outage: simulate unreadable, malformed and lock-failed canonical state. Security returns unavailable/503, health becomes DEGRADED, the userscript retains its token and pairing id, and subsequent recovery resumes heartbeat without pairing or canonical-file overwrite.
- Authoritative capability loss: a successfully read store containing revoked state or no matching pairing returns revoked/unknown, produces reason-coded 401 and PAIRING_REQUIRED, refuses renewal, and causes the userscript to clear the credential only on that verdict.
- Restart recovery: pair once, rebuild daemon/security/control/health stores, then heartbeat from a new browser tab instance using the persisted capability. Verify no redemption occurs and Web Sol reaches AVAILABLE only after a successful new probe generation.
- Signal separation: fresh bridge presence with the 8765 listener unavailable is OFFLINE `bridge_unreachable`; a reachable listener with stale claim presence is OFFLINE `no_browser_presence`; a fresh 8765 path with stale 8770 heartbeat is non-AVAILABLE in scheduler and browser.
- Probe truth and isolation: a probe cannot succeed without an observed exact response marker and nonce; timeout and malformed responses are classified; reserved probe records never enter `websol-decisions.json`, affect transitions or collide with ordinary request identities.
- Duplicate/stale binding: two live tabs produce DEGRADED and no delivery, while an active session on a conversation different from the project binding cannot receive work or an AVAILABLE snapshot.
- Failover exactness: prepared and submitted occurrences use the same `(project_id, run_id)` across dispatcher, failover store and `ai_review:<run_id>`, even when a newer transition exists. Assert later reviewer `advance()` does not launch a duplicate.
- Crash reconciliation: restart after intent creation, revocation request, finalized withdrawal, dispatcher marking and reviewer submission. Every case converges to response-wins or exactly one review; attempt exhaustion becomes visible unavailable state plus one deduplicated incident.
- No AGY capacity mutation: strict fakes prove Web Sol failover does not call routing-pool acquisition, active-request telemetry is unchanged, and resource evidence is copied from the actual reviewer execution result.
- Multi-project isolation: failure, cancellation, probe generation, token verdict and failover for one binding do not change another project's health or delivery.
- Focused suites cover health, capability recovery, adapter state, probes and failover; adjacent bridge, dispatcher, response-consumer, reviewer, web, CLI and daemon suites remain passing, followed by the full `tests_py` regression, `python -m compileall src` and `git diff --check`.
- Run `graphify update .` after implementation and verify the resulting graph query connects the health source to dispatcher, control heartbeat, userscript, probe and failover paths.
- Collect live operator evidence across independent daemon and Chrome restarts, a listener-down split-brain case and one real probe. In Windows PowerShell 5.1 use `;` plus explicit `$LASTEXITCODE` checks, never `&&` or `||`, preserving `seed:p11b:rdc-powershell-5.1`.

### Risks / failure modes
- A late ChatGPT response may race cancellation. Mitigation: cancellation never shortens the already-issued lease, the exact response may win until its persisted deadline, and reviewer submission waits for final withdrawal.
- Without durable cancellation fields, restart could restore infinite reclaim behavior. Mitigation: cancellation request/deadline and withdrawn tombstone live in the queue record, and claim/renew/submit all fail closed against them.
- An excessively short maximum claim lifetime could cancel legitimate slow answers. Mitigation: align the configurable default with the existing 15-minute browser wait limit, expose reason/timing telemetry and test boundary behavior.
- A stale AVAILABLE snapshot could mislead the browser. Mitigation: exact binding key, short `valid_until`, conservative heartbeat-side binding/tab checks and demotion-only local logic; no local signal independently promotes LIVE.
- Treating malformed canonical security data as unknown could erase recoverable credentials or overwrite evidence. Mitigation: classify it as unavailable, return 503, preserve the userscript token and refuse all mutations until authoritative state is readable.
- Capability rotation across several tabs could invalidate peers. Mitigation: retain stable pairing identity and a bounded previous-token grace period; duplicate tabs still keep availability DEGRADED.
- Real probes consume conversation turns and quota. Mitigation: generation invalidation, persisted exponential backoff, hard attempt cap, reserved identity and steady-state cadence tests.
- Probe responses could be consumed as workflow decisions. Mitigation: reserved request namespace, consumer exclusion and exact probe discard, all covered by regression tests.
- Concurrent health/control/daemon access on Windows could expose partial JSON or lock contention. Mitigation: atomic writes, interprocess locks, bounded operations and fail-closed reads.
- Occurrence failover may lack a valid AIBroker transition. Mitigation: report FAILOVER_UNAVAILABLE with an incident and durable reason instead of silently stalling or fabricating a route.
- The expanded daemon tick includes HTTP probing and reconciliation. Mitigation: strict timeouts, cached listener checks, attempt caps and exception isolation so health failures degrade the resource rather than stop orchestration.
- Userscript behavior depends on Tampermonkey and ChatGPT DOM details. Mitigation: keep authority/security logic in pure tested functions, feature-detect GM APIs and require a live-browser evidence run.

### Out of scope
- Replacing or merging the separate 8765 bridge and 8770 control services.
- Changing Web Sol request/response identity, decision vocabulary, prompt marker protocol or Decision Guard semantics.
- Supporting browser providers or adapters other than the existing ChatGPT Web userscript.
- Launching, focusing or closing browser tabs, automatically rebinding conversations, or choosing among duplicate tabs.
- Redesigning AGY pool scoring, adding Web Sol to AGY capacity accounting, or acquiring/pinning pool resources for AIBroker failover.
- Building a general-purpose failover execution engine beyond the existing exact-occurrence AIBroker reviewer path.
- Changing P16.10 detector architecture; this task only emits deduplicated incidents through its existing harvesting path.
- Removing the manual pairing and forget commands; manual pairing remains the explicit recovery for genuinely revoked or authoritatively unknown credentials.
- Mobile pairing/device flow changes beyond preserving compatibility with the stricter canonical capability-store loader.
- Guaranteeing uninterrupted service when the canonical capability file is actually lost or revoked; those cases intentionally require PAIRING_REQUIRED.
